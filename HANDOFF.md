### 2026-10-06 (cloud, mobile-engineer) — hotfix: push-registration loop, child refetch limits, 429, HUD error boundary (`fix/mobile-child-refetch-loop`)
Incident (TestFlight 1.24.4 from main incl. PR #39/#40/#43): legacy mutt (pet 3) at the vet until 10:41:01 Ljubljana; Caddy logged **429** on `GET /api/child/pet` at 08:40:16, 08:41:15, 08:41:24, 08:42:01 UTC; iOS "PetPrep crashed"; after relaunch the dead "Kužka ni bilo mogoče naložiti" screen under a lock card "do 08:41" (UTC). Mobile only.
- **ROOT CAUSE (server evidence + Jest reproduction):** Caddy, this child, 08:36–08:42 UTC: `POST /api/devices` **58–60 ×200 plus 869 / 280 / 193 / 1 650 / 1 304 / 1 395 ×429 per minute**; `GET /api/child/pet` only 1–2/min, 429 because `throttle:api` (60/min per user, all `/api/*` routes) was drained by `/devices`. The loop: `mobile/src/modules/push/usePushNotifications.ts:35-37` (main @ b1e1fbf) — `Notifications.addPushTokenListener(() => { void registerForPush(); })`. On iOS `registerForPush()` → `getExpoPushTokenAsync()` → `getDevicePushTokenAsync()` → `UIApplication.registerForRemoteNotifications()` → `didRegister` resolves the promise **and emits `onDevicePushToken` again** (expo-notifications 57.0.21 `ios/ExpoNotifications/PushToken/PushTokenModule.swift#didRegister`), even for an unchanged token → the listener re-registers → forever, at network speed; `registerForPush` had no in-flight guard, no dedupe and no backoff, and a 429 didn't stop it (the echo fires before the POST). Started on the first sign-in / restore with notification permission granted (M3-02, PR #35).
