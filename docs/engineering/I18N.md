# Internationalisation (M1-18)

Status: **core built 2026-10-07** (`feat/M1-18-i18n-core`); screens migrate namespace by namespace.

## Decisions
- Languages: **English (default, fallback) + Slovenian**; more later (global market). David, 2026-10-02.
- Language = the user's explicit choice on this device (SecureStore `petprep.language`) → else the
  device's first supported preferred language → else English.
- Switch: compact `EN | SL` on the start screen (before login — a child may not read the device
  language) and "Jezik / Language" card in the parent Nadzor tab. Per device, not per account.
- The app sends `Accept-Language: en-GB | sl-SI` on every API request. Push notifications are sent
  later by a queue, so the server must **store** the language per push device (body field `locale`
  on `POST /api/devices` — not the header, which iOS also sends on its own)
  — backend part of M1-18, see "How it works (backend)".
- The in-app choice wins over the system per-app language setting (iOS Settings / Android 13+):
  after an in-app choice, changing the system setting has no effect until the app is reinstalled.
- Android: `resourceConfigurations` now keeps only en + sl resources of libraries (smaller app);
  a new language must be added to the plugin's `supportedLocales`.
- Native permission texts (iOS Info.plist) are localised via `mobile/locales/<lang>.json`
  (`app.json` → `locales`); `expo-localization` plugin declares `supportedLocales` (Android 13+ /
  iOS per-app language). **Needs a new native build.**

## How it works (mobile)
- `mobile/src/i18n/` — `index.ts` (i18next instance, `t`, `setLanguage`, `loadSavedLanguage`,
  `currentLanguage[Tag]`), `language.ts` (pure helpers), `resources.ts` (namespaces),
  `strings.ts` (`strings()` view), `locales/<lang>/<namespace>.json`.
- Namespaces: `common, auth, child, behaviour, training, contract, parent, family, account, pet,
  push, paywall`. English is the reference; key types come from `locales/en/*.json`.
- `__tests__/parity.test.ts` fails when a language misses a key, has an extra key, a different
  `{{placeholder}}`, an empty string, or plural forms that don't match its CLDR categories
  (en `_one/_other`, sl `_one/_two/_few/_other`).
- Jest runs with a Slovenian test device (`jest.setup.ts` mocks `expo-localization`), so existing
  tests keep asserting Slovenian copy; English is tested with `i18n.changeLanguage('en')`
  (reset to `sl` in `afterEach`).

## Migrating a string table
The app keeps its per-screen `*_STRINGS` objects, now backed by i18next:

```ts
// before
export const CHILD_PIN_STRINGS = {
  title: 'Vpiši svojo kodo',
  rateLimited: (time: string) => `Preveč poskusov. Počakaj še ${time}, potem poskusi znova.`,
} as const;

// after — locales/sl/auth.json + locales/en/auth.json: { "pin": { "title": "…", "rateLimited": "… {{time}} …" } }
export const CHILD_PIN_STRINGS = strings('auth', 'pin', {
  rateLimited: (time: string) => t('auth:pin.rateLimited', { time }),
});
```

Rules:
1. Plain strings → JSON leaves (read lazily through the `strings()` proxy). Functions → `{{vars}}`
   in JSON + an explicit function in the third argument (nested objects allowed:
   `{ errors: { tooMany: (n) => t(…) } }`).
2. Hand-written Slovenian plurals (`n === 1 ? … : n === 2 ? …`) → i18next plurals:
   `"dogs_one": "{{count}} pes", "dogs_two": "{{count}} psa", "dogs_few": "{{count}} psi",
   "dogs_other": "{{count}} psov"` (sl) and `"dogs_one" / "dogs_other"` (en); call
   `t('family:x.dogs', { count })`.
3. Never put a translated value in a module-level constant or in `useMemo` without the language
   as a dependency. Screens/components that host language-dependent memoised text call
   `useTranslation()`.
4. Inline JSX literals and `accessibilityLabel`s count too. Brand names (PetPrep) stay.
5. Dates / times: format with `currentLanguageTag()` when using `Intl`; hand-built Slovenian
   phrases ("jutri ob 18:00") become keys with placeholders.
6. Comparisons against server values must not use translated text (use codes).
7. Don't end an ordinary key with `_one/_two/_few/_many/_other/_zero` — i18next reads it as a plural form.
8. English copy: natural, short, kind for the child (2nd person, "you"), polite and clear for the
   parent. Slovenian copy stays exactly as it was (tests rely on it).

## How it works (backend)
Branch `feat/M1-18-i18n-backend` (2026-10-07).

- **Supported languages in one place:** `backend/config/locales.php` (`supported => ['en', 'sl']`,
  `default => 'en'`). Texts: `backend/lang/<locale>/<file>.php` (`push.php`, `account.php`); English
  is the reference, a Pest test fails when a language misses / adds a key.
- **Request language:** middleware `App\Http\Middleware\SetRequestLocale` (prepended to the `api`
  group) → `App\Support\RequestLocale::resolve(Accept-Language)` → `App::setLocale()`. Primary
  subtag only (`sl`, `sl-SI`, `sl_SI`, `SL`), q-values honoured (ties keep header order), `q=0`,
  `*`, unsupported tags and garbage skipped; header cut at 512 bytes / 20 ranges. Nothing supported
  → `en`. Always set (no leak between requests in a long-lived worker); answers carry
  `Content-Language` and `Vary: Accept-Language`. It decides response texts only.
- **Push texts per device:** `device_push_tokens.locale` (nullable). `POST /api/devices` stores the
  language only from the explicit body field `locale` (`en` | `sl`, validated against
  `config/locales.php`, anything else → 422) and refreshes it whenever it is sent. **Not from
  `Accept-Language`:** installed iOS builds (2.0.2) send an implicit one (iOS adds e.g.
  `en-US,en;q=0.9` because the bundle declares no localisations), so old builds do *not* send "no
  header" — deriving the push language from it would flip Slovenian installs to English. Without
  `locale` the stored value is kept; a new row gets `config('locales.unstated_device')` = `sl`
  (only pre-M1-18 builds omit it, and they are Slovenian-only). `NotificationService::message()`
  (run by the `SendPushNotification` job) renders title + body per device with
  `PushCopy::title/body(…, $device->locale)` (null / unknown → `en`, a safety net only). One
  notification row, one dedupe, same ≤ 100-per-request chunks — each Expo message simply carries
  its own body, so mixed-language batches need nothing special.
- **Backfill:** the migration `2026_10_18_120000_add_locale_to_device_push_tokens` sets every
  existing row to `sl` — all installs before M1-18 ran the Slovenian-only app, so their pushes stay
  exactly as before until the new build re-registers with `locale`. (Its date stays after
  `2026_10_10_120000_create_push_notification_tables`, which creates the table; an earlier date
  would break `migrate:fresh`.) Slovenian push copy is byte-identical to the pre-M1-18 `PushCopy`
  constants (dataset test).
- **Deletion word:** `ConfirmDeletionRequest` takes an optional `confirm_word`; once the key is
  present it must be the word of **any** supported language (`account.deletion.confirm_word`:
  `IZBRIŠI`, `DELETE`) — empty, blank or null is refused. Normalisation: Unicode NFC (when
  ext-intl is loaded), trim, upper case (`š` required). Optional so app builds before M1-18 keep
  working. Validation messages of that request come from `lang/*/account.php`.
- **Export:** `about` and the download file name (`petprep-export-…` / `petprep-izvoz-…`) follow the
  request language; `push_devices[].locale` is exported.
- **Stays English / untranslated on purpose:** machine fields (`reason`, `codes`, enum values,
  `pet_state`), the remaining English `message` strings (the apps show their own text per
  `reason`), Laravel's default validation messages (no `lang/sl/validation.php` yet — Slovenian
  requests fall back to English), webhook answers, logs, Filament admin, audit notes and code
  comments (Slovenian phrases in comments of `ActivityType`, `ClientFeature`, `PetLockReason`,
  `Pet`, `HygieneEventService`, `EscalationService`, `TrainingPayload`, `BehaviourEventService`,
  `TrainingService`, `PetActivityService`, `FamilyDashboardService`, `ChildPetController` only
  quote app copy — none reaches a user).
- **Mobile:** the app sends `locale` on `POST /api/devices` (and again after a language switch) and
  `confirm_word` with the typed word.
- **Add a language:** add the code to `config/locales.php`, copy `lang/en/` to `lang/<code>/` and
  translate; no migration (the `locale` column has no CHECK on purpose).
