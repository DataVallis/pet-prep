## 2. Data model (PostgreSQL)

**Family model (M2-01, ADR-012).** A family has several parents and several children; each child cares for its own pet or several children share one pet. Ownership and authorization go through `families` / `family_user` / `pet_caretakers`; `users.parent_id`, `users.timezone` (of a parent) and `pets.user_id` are **deprecated mirrors** kept in sync for current app builds (model hooks on `User` / `Pet` / `QuietHours` map writes of the old columns into the family model; removal = follow-up M2-01b).

**families** — `id, timezone (IANA string(64), default Europe/Ljubljana), timestamps`. The **family timezone** for every wall-clock rule (`User::familyTimezone()` / `Pet::familyTimezone()` read it; before M2-01 it was the parent's `users.timezone`, which is still mirrored for every parent). The pet, not the family, is the billing unit (49.99 € per pet, BUSINESS_MODEL).

**family_user** — `id, family_id → families (**restrict**), user_id → users (unique, cascade: one family per user), role (parent|child, CHECK), timestamps`. Index `(family_id, role)`.

**family_invites** — second-parent invite codes: `id, family_id, created_by → users, code (unique, 8 chars from ABCDEFGHJKMNPQRSTUVWXYZ23456789), expires_at (24 h), used_at, used_by → users, timestamps`. Single use; a new code from the same parent expires their previous unused one.

**pet_caretakers** — `id, pet_id → pets (cascade), user_id → users (the child; **nullable, SET NULL since PR #29** — null = a deleted child's tombstone), started_at / ended_at (nullable, PR #29: caretaker history — a deleted child's row on a shared pet is kept with user_id null, started_at = their start (contract / birth), ended_at = deletion time; `CareScoreService` counts it as a sharer of every routine that opened while it was caring, so the remaining children's past fair share doesn't change; `PetCaretaker::active()` / `Pet::caretakers()` / `caretakerRows()` / recipients / dashboard lists use active rows only), pet_is_active (copy of pets.is_active maintained by the triggers `pet_caretakers_copy_pet_is_active` (BEFORE INSERT/UPDATE) and `pets_sync_caretaker_is_active` (AFTER UPDATE OF is_active on pets) — never written from PHP), requires_contract (true = must sign their own contract before acting; false only for rows backfilled from pets born before contracts — grandfathered), timestamps`. Unique `(pet_id, user_id)`; **partial unique index `pet_caretakers_one_active_pet_per_child (user_id) WHERE pet_is_active AND ended_at IS NULL`** (ended rows ignored since PR #29) = a child cares for at most one active pet (MVP choice, pending David). Every pet has ≥ 1 caretaker (service rule; `Pet::created` adds `pets.user_id` when that user is a child — legacy pets owned by a parent account have none and are logged by the migration). The trigger reads the pet `FOR SHARE`.

**Deletes never cascade from a family into child data** (PR #14 review): `pets.family_id`, `family_user.family_id`, `quiet_hours.family_id` are `ON DELETE RESTRICT`; only `family_invites` cascade. Lock order for family writes: parent user row → child user row → family row (`PairingService::pairChild`, `FamilyInviteService::joinFamily`).

**Account deletion (M2-08) = `AccountDeletionService` only** (API + Filament; Filament has no plain user delete any more). Immediate, irreversible, one `DB::transaction(…, 3)` (retried on deadlock / serialization failure) that first locks **every parent row of the family (id order), every child row (id order), the family row, then the pet rows** (PR #29). A full-family purge also deletes **orphaned legacy child accounts** (role child, `parent_id` → one of its parents, no family); a leaving parent's legacy pets in **other** families are deleted (ledger detach + files), never left to the cascade. Password confirmation: `confirmPassword($user, $password, scope)` — 5 **failed** attempts / 15 min per user, separate scopes `account` / `child` (429 `too_many_attempts` + `Retry-After`; a success clears the counter). **Watch the cascading deprecated mirrors:** `users.parent_id`, `pets.user_id` and `quiet_hours.parent_id` are `ON DELETE CASCADE` — deleting a user without re-pointing them first deletes children / pets / quiet hours. So: a parent leaving a family that keeps another parent hands the family's quiet-hours row, the children's `parent_id` and legacy parent-owned pets to that parent; a deleted child's shared pet gets `pets.user_id` = the next caretaker; users outside the purge whose `parent_id` points into it get `parent_id = null`. Pets are deleted with a query-builder delete (no model events) after `AiSpendLedger::detachPets()`; their rows cascade (activities, contracts incl. signatures, caretakers, per-child steps, walks, routines, status periods, hygiene events, PINs, media slots) and the files go in the queued `DeletePetMediaFiles` job **after commit**. Deleted child on a shared pet: `activities_log.actor_user_id` / `pet_daily_routines.actor_user_id` → null (FK `SET NULL`; the rows keep counting for the pet), the caretaker row becomes a **tombstone** (user_id null, started_at kept, ended_at = now — PR #29), the child's contract and `pet_daily_steps` rows go (today's steps stay in `pets.daily_step_count` and are attributed to the primary caretaker on the next sync). Also deleted per user: Sanctum tokens, `sessions`, `password_reset_tokens` (by e-mail). One audit log line per deletion (`Account deletion: family_deleted | parent_removed | parent_deleted | child_deleted` with family id + counts, no names / e-mails / user ids). Superadmins can't be deleted (API 403 `superadmin_protected`; Filament refuses a family with a superadmin member).

**pet_daily_steps** — each child's own steps per family-local day on a pet: `id, pet_id, user_id, local_date, steps, last_sync_at (anti-cheat reference per child), timestamps`. Unique `(pet_id, user_id, local_date)`. The pet's `daily_step_count` (→ energy, daily walk) = sum over its caretakers; steps the pet has that no row explains (from before M2-01) belong to the primary caretaker.

**users** — `id, name (a child's **nickname**, ≤ 30 chars via the API; a parent's display name, ≤ 60 at sign-up), birth_year (smallint, nullable, CHECK 1900–2100 — the only age datum of a child, M2-02), email (**nullable since M2-02**, unique — PostgreSQL treats NULLs as distinct; stored lower case by `/api/register`, compared case-insensitively by register + login + Filament via `lower(email)`; functional index `users_email_lower_unique` (UNIQUE) — or `users_email_lower_index` (plain, colliding ids logged) if legacy rows already differ only in case, PR #25), email_verified_at (nullable, not used yet — M2-10b), terms_accepted_at (nullable, **M2-10a**: when a self-registered parent accepted the terms of use + privacy policy; null for seeded / admin parents and every child), terms_version (string(32), nullable, PR #25: which legal-text version was accepted, from `config/legal.php`; never returned by the API), password (**nullable since M2-02**; PIN-only child profiles have neither), role (parent|child, CHECK), timezone (IANA string(64), NOT NULL, default `Europe/Ljubljana`; for a parent a mirror of `families.timezone` since M2-01), is_superadmin, parent_id → users (cascade; **deprecated** — the parent who paired the child), pairing_pin(6), pin_expires_at, pairing_pet_id → pets (nullable, null on delete: the child PIN joins this existing pet; null = the PIN creates a new pet), revenuecat_id (unique), timestamps`. Indexes: `parent_id`, `pairing_pin`. All timestamps stay UTC (`APP_TIMEZONE=UTC`).

**pets** — `id, user_id → users (child; **deprecated** = primary caretaker, the child the pet was created for), family_id → families (NOT NULL, **restrict**), breed_type (mutt|border_collie|domestic_cat|maine_coon, CHECK), species (**M5-R06-01**: dog|cat, NOT NULL default dog = backfill of every existing pet, CHECK `pets_species_check`; CHECK `pets_species_breed_check` = species of the breed — cat breeds domestic_cat / maine_coon; set from the breed by `Pet::creating/saving`, also on an admin breed change), name (**M5-R08**: varchar(40) nullable — optional label set by a parent via `PATCH /api/parent/pets/{pet}/name`, ≤ 20 characters validated in `UpdatePetNameRequest`; null = no name; never used in push texts, server sentences or AI prompts; deleted with the pet row; in the family export), pet_dna JSONB (GIN), current_video_url, hunger_level, thirst_level, energy_level, hygiene_level (double precision 0–100, CHECK; Eloquent cast `float`; every API/broadcast/Filament output rounds half up to int via `Pet::displayMetric()` / `Pet::attributesToArray()`), daily_step_count, last_step_reset_at (start of the current family-local step day; set at birth), last_step_sync_at (device time of the last accepted step sync — anti-cheat reference, cleared at midnight), last_decay_at (decay clock, nullable; set at birth — on create for a born pet, at contract signing for a paired one; backfilled to migration time), frozen_at (start of the current hard stop / illness freeze, null otherwise), hygiene_scheduled_through (date: last family-local day whose hygiene events exist), born_at (**nullable, no default since M1-07b**: null = unborn — paired, waiting for the contract; set to the signing moment by `POST /api/child/contract`; pets created before M1-07b kept theirs = grandfathered as born, even without a contract), is_active, pet_state (CHECK: idle|sleeping|low_energy|hungry|sick|playing), illness_until (null again after recovery), walk_illness_due_at (planned start of a missed-walk illness — daily walk rule), escalation_level (0–3), {hunger,thirst,hygiene}_zero_since (neglect clocks), energy_zero_since (unused since the daily walk rule, always null), is_game_over, is_hard_stopped, certificate_eligible, origin (bought|adopted|null, CHECK — M5-R01), arrival_age_months (smallint ≤ 300, nullable — the dog's age when it came home, parent's choice), life_stage (puppy|young|adult|senior|null, CHECK; only with an arrival age, CHECK `pets_life_stage_profile_check` — the stage of **today's** rules, set at creation and written by the decay tick), timestamps`. **All three NULL = legacy profile** (PR #37 review B1; **permanent — David 2026-10-05**, also after the challenge ends): every pet created before M5-R01, from a PIN without a profile (`pet_options` null — issued before M5-R01 or by an app build without the profile picker) or through the deprecated `/child/pair` keeps exactly the pre-M5 rules (breed `feed_windows`, `daily_steps_required`, no parent-covered meals, no stage, no stage images, stored DNA prompt) for good — `Pet::isLegacyProfile()`; no column defaults, nothing is backfilled. Index `(user_id, is_active)`. **Age (M5-R01)** = `arrival_age_months` + completed weeks since `born_at` (7 family-local days at the birth's wall-clock time — DST never moves the birthday hour; `LifeStageService::ageMonthsAt`); an unborn pet is as old as it arrived. `virtual_age_months` in the API stays the 12-week challenge clock (program weeks since birth, absolute 7 × 24 h). **Program clock (M3-11b, David 2026-10-07):** both clocks skip the time inside `payment_lock` status periods — `Pet::programBirthAt($at)` = `born_at` + payment-lock seconds before `Pet::programInstantAt($at)` (= `$at`, or the lock start while `$at` is inside a lock), `Pet::programSecondsAt()` → `virtualAgeInMonths()` / `hasReachedSimulationEnd()`, `LifeStageService::weeksSinceBirth()` / `nextTransition()` count from the effective birth, `CareScoreService::progress()` subtracts the lock seconds since the child's start. Spans are read once per model instance (`Pet::paymentLockSpans()`, eager-loadable `paymentLockPeriods` relation — `FamilyDashboardService::family()` does; the `created` / `updated` hooks and `refresh()` forget them). Lock periods start at `payment_locked_at` = the instant the lock was due (`ChallengeService::lock($pet, $now, $since)`: the birth for a lock at birth (M3-13, `lockAtBirth`), `trial_ends_at` for an expired pre-M3-13 trial, so a late tick / scheduler outage is excluded, the tick time for a pet without a trial that the tick locks; the refund time for a refund re-lock; clamped by `PetStatusPeriodService::paymentLockStart` to [birth, now] and after the previous lock's end). No spans query for a free / unborn pet or an unpaid, unlocked challenge still inside its trial (provably never locked). Past instants never shift (a later lock lies after them); hard stop / illness / inactive still count; `born_at` / `trial_ends_at` unchanged. DST: the effective birth is shifted in absolute seconds, so a DST change inside a pause moves the weekly birthday's local hour by one hour.

**pets — plan / trial / payment (M3-11, `docs/product/PAYMENTS_SPEC.md`)** — `plan` (free|challenge, NOT NULL default `challenge`, CHECK `pets_plan_check`; fixed at creation from the PIN), `trial_ends_at` (**M3-13, David 2026-10-08 — no free trial: = `born_at`**, set by `Pet::giveBirth` / on create of a born pet; pets born before M3-13 keep birth + 7 family-local days, `Pet::trialEndFor`; column kept, expand-only; the P7 per-child rule `childHadTrial` / `trialEndAtBirth` was removed); null before birth and for a free pet), `challenge_paid_at` + `challenge_paid_source` (purchase|grandfathered, CHECK `pets_challenge_paid_check`: both or neither), `payment_locked_at` (the game-loop freeze of an unpaid born challenge — since M3-13 set at birth by `ChallengeService::lockAtBirth` in `signContract`, or by the tick when a pre-M3-13 trial ends — part of `Pet::isFrozen()`; its `payment_lock` status periods are excluded from the program clock, M3-11b), `trial_reminder_sent_at` (hidden; legacy — the day-6 push is no longer sent since M3-13). CHECK `pets_free_plan_check`: a free pet has no trial / payment / lock. Partial index `pets_unpaid_trial_idx (trial_ends_at) WHERE plan='challenge' AND challenge_paid_at IS NULL`. **Backfill:** every pet existing at migration time = `challenge`, paid `grandfathered` (paid_at = born_at ?? created_at), `trial_ends_at` = born_at + 7 days. **Status** is derived only by `Pet::challengeStatus()`: free → null; paid › trial (only a pre-M3-13 trial still running, a born row without `trial_ends_at`, or any unpaid pet while `payments.enforced` is false) › payment_required (M3-13: also unborn — buy before the contract; `awaitsPayment()` ignores unborn pets, so their lock reason stays `contract_required`). **Plan payload** (`PetPlanPayload`, child state `pet.plan`, dashboard `pets[].plan`, `PetUpdated.plan`, activate): `{type, status, trial_ends_at, paid_at, payments_enforced, display_type}` — `display_type` (M5-F02, additive) = the plan a parent sees: `free` for a free pet and for a breed without premium (mutt) whose challenge is paid but not by a purchase (`grandfathered` / `admin`), else = `type`; display only (`type` / `status` stay the real plan). **`converted_to_free_at`** (M5-F02 QA, migration `2026_10_21_120000`): set when an unpaid mutt challenge became `free` (`ChallengeService::convertUnpaidMuttToFree`); a free pet with it set still reads its `payment_lock` periods in `paymentLockSpans()`; CHECK `pets_converted_free_check` (only on `plan = 'free'`). `Pet::creating` defaults `plan` by breed and turns an unpaid mutt challenge into `free`; `markRefunded` on a mutt converts instead of locking.

**activities_log** — `id, pet_id → pets, actor_user_id → users (nullable, null on delete — the child who did it, M2-01; null for system rows: escalation), activity_type (fed_pet|watered_pet|walked_pet|cleaned_poop|ignored_warning|signed_contract|parent_fed_pet, CHECK), value int nullable, created_at`. Indexes `(pet_id, created_at)`, `(actor_user_id, created_at)`. Backfill: child-action rows got `pets.user_id`, `ignored_warning` rows stay null. `value` conventions for `ignored_warning`: 30 = phase 1, 10 = phase 2, 0 = phase 3, −1 = illness, −2 = game over; `walked_pet`: one row per day when a step sync first reaches the daily goal, value = the day's steps (not one row per sync — the dashboard counts a walk once); `fed_pet` / `watered_pet`: the hunger / thirst % shown just before the action; `cleaned_poop`, `signed_contract`: null. `fed_pet` / `watered_pet` rows are also the source of truth for "already fed in this window" / "water used today" (M1-07). **`parent_fed_pet` (M5-R01)** — system row (actor null, value = hunger shown before): a meal whose feed window lies entirely in quiet hours was given by the parent (decay tick at the window start); it counts as "this window is fed" but is never a child routine and never in the child's stats. **M5-R02 (David 2026-10-06):** child actions `took_out_pet` ("Pelji ven", value null — not a routine itself) and `resolved_chewing` ("Pospravi in daj igračo", resolves a chewing routine like `cleaned_poop` a mess); system rows (actor null, value null, `created_at` = the event instant) `pet_accident` and `pet_chewed` for the parent timeline (`is_positive: false`).

**breed_configs** — every tunable game number (M1-06), mutt | border collie | domestic cat | maine coon (cats since M5-R06-01, hidden): `breed_slug (mutt | border-collie | domestic-cat | maine-coon), daily_steps_required (4000 | 10000 | 0 | 0), hunger_decay_rate (8 | 12 | 8 | 8 %/h), thirst_decay_rate (10 | 15 | 8 | 8 %/h, CHECK ≥ 0), poops_per_day (1 | 2 | 0 | 0, CHECK 0–10), feed_windows (jsonb list of family-local [start, end) "HH:MM" pairs, default [["06:00","10:00"],["17:00","21:00"]], CHECK array), water_times_per_day (3 | 3 | 2 | 2), water_min_gap_minutes (180 | 180 | 240 | 240), premium_unlock (false | true | false | true; **exactly one free breed per species**, enforced by `BreedConfig::saving/deleting` + Filament — QA PR #91), species (M5-R06-01: dog|cat, CHECK; for an enum breed always the enum's species — `BreedConfig::saving`), sort_order (int, picker order), search_keywords (jsonb array, CHECK), label_key (i18n key, e.g. `breeds.maine_coon`)`. **`premium_unlock` is the single source of free / paid since M5-R06-01** (`BreedType::isPremium()` → `BreedCatalogService`, cached 300 s + per-request memo, forgotten on model save / delete and by the seeder; enum `defaultPremium()` only for a breed without a row). Cats (seeded insert-only): domestic-cat free / maine-coon paid, hunger and thirst 8 %/h, water 2 / ≥ 240 min, poops_per_day 0 (litter = M5-R06-05), daily_steps_required 0 (no steps; energy stays 100 %). Column defaults = mutt values (backfill for existing rows). `BreedConfigsSeeder` upserts by slug and runs on every production deploy (overwrites Filament edits — open question). The prompt is built only from breed + traits + fixed photo style — never from names or other personal data. **Cats (M5-R06-07):** `PetAppearancePrompt` picks the template by the breed's species (`speciesOf()`): `CAT_STYLE` / `CAT_NEGATIVE` / `CAT_EDIT_KEEP` / `CAT_ADOPTED_AVOID` / `CAT_VIDEO_STYLE` / `CAT_VIDEO_NEGATIVE` — no cat prompt contains the word "dog"; dog prompts are byte-identical (`DogMediaPromptSnapshotTest`). `config/breed_appearance.php` has `domestic_cat` (unsourced draft) and `maine_coon` (FIFe C16 traits) — both `verified: false` — plus two optional cat-only keys: `features` (fixed breed features appended to the description: Maine Coon frill, square head, coat longer down the back) and `stage_notes` (an extra sentence after the stage cue: Maine Coon kitten bigger with tufts, young Maine Coon not fully grown — C17). **A cat always gets DNA v2** (`PairingService` never calls the v1 builder for a cat, even with `AI_PET_DNA_VERSION=1`; `FalAiService::generateInitialPetDna`, `PetAppearancePrompt::legacyPromptForPet` and a cat prompt without traits throw; `PetMediaService::generateReferenceImage` leaves a cat without DNA v2 at `media_status=disabled`).

**ai_spend_ledger** (M4-07) — one row per fal.ai call: `purpose (lab|reference_image|state_video), profile, endpoint, unit (image|megapixel|second), units, cost_usd (ESTIMATE from config/media.php list prices), status (reserved|committed|void), error_reason, request_id, pet_id → pets (null on delete), pet_media_id → pet_media (null on delete, M4-03), media_lab_result_id → media_lab_results (null on delete), timestamps`. **Rows outlive pets (M2-08):** `AiSpendLedger::detachPets($petIds)` nulls `pet_id` + `pet_media_id` **before** any pet delete (`Pet::deleting` hook, `AccountDeletionService`) — left to the two `ON DELETE SET NULL` FKs, a row linked to both the pet and its slot fails the DELETE (PostgreSQL re-checks `pet_media_id` while setting `pet_id` null, after the slot is gone); the cost stays for accounting. Caps count `reserved + committed`, in **two separate budgets** (PR #22 review): production (`reference_image`, `state_video`) vs `AI_DAILY_BUDGET_USD` / `AI_MONTHLY_BUDGET_USD`, and `lab` vs `AI_LAB_DAILY_USD` / `AI_LAB_MONTHLY_USD` (refusal `budget_lab`) — the lab can never starve new pets. **Settlement:** `void` only when nothing reached fal (cURL 5/6/7/35/51/58/60, or 28 "Resolving / Connection timed out") or fal answered 4xx/5xx; a timeout / reset **after sending** → `committed` with `error_reason = http_error` (fal may still run and bill it); a 2xx queue answer without `request_id` → `committed` + `invalid_response`.

**media_lab_runs / media_lab_results** (M4-02 AI Lab, admin only, no child data) — run: `user_id (superadmin), kind (image|video), breed, fixed_traits, samples, profiles[], pet_state, source_result_id (image animated by a video run), estimated_cost_usd`; result: `kind, profile, endpoint, sample_index, seed, traits, prompt, negative_prompt, params (exact fal input), source_image_url, request_id (unique, fal queue), status_url / response_url (queue.fal.run only), status (queued|running|completed|failed|unknown — `unknown` = video submit sent but the answer was lost: no `request_id`, nothing to poll, cost kept), error_reason, error, result_url (*.fal.media only), latency_ms, estimated_cost_usd (charged estimate; 0 when refused)`.

**quiet_hours** — one row per **family** (M2-01): `parent_id → users (unique; the parent who created it — handed to a remaining parent when its creator moves to another family), family_id → families (unique, restrict), school_start/end, bedtime_start/end (time), is_active`. Any parent of the family reads / edits it; `Pet::quietHours()` reads by `family_id`. **Every family has quiet hours (fix/quiet-hours-default, 2026-10-08):** `QuietHours::DEFAULTS` (bedtime 21:00–07:00 family-local, no school window, `is_active` true) is the single source. `FamilyService::addMember()` → `ensureDefaultQuietHours()` inserts it (insert-or-ignore, never touches an existing family row or a parent's legacy row) when the first parent joins a family — registration, `User::booted` bridge (`ensureFamilyFor`), any parent membership. Data migration `2026_10_22_120000_backfill_default_quiet_hours` inserted it for existing families without a row (first parent without a row; insert-only, idempotent, `down()` no-op). A family that cannot own a row (no parent — legacy) reads the same defaults in code: `Pet::quietHours()` is **never null** (unsaved `QuietHours::defaultFor($family)`), and `RoutineLedgerService` uses the same fallback. `is_active = false` is the parent's explicit choice (no quiet time at all). `GET /api/parent/dashboard` `quiet_hours` carries the same `saved` flag (applied defaults when no row). Closed `pet_daily_routines` days are never recomputed; the default applies from the next tick.

**child_login_pins** (M2-02) — one-time PINs a parent issues **for a specific child profile**: `id, family_id → families (cascade), child_user_id → users (cascade), created_by → users (null on delete), pet_id → pets (nullable, cascade: join target), pin_hash (HMAC-SHA256 of the 6 digits with `APP_KEY` — the PIN itself is never stored), expires_at (15 min), consumed_at, revoked_at, pet_options jsonb (M5-R01: `{breed, origin, age_stage}` of the new pet, only for `new_pet` PINs), pet_options also carries `species` (M5-R06-01, last key; absent on older PINs = the breed's species), plan (M3-11, free|challenge|null, CHECK — the new pet's plan, only for `new_pet` PINs; null = PIN from before M3-11 → `challenge`), timestamps`. **Partial unique index `child_login_pins_open_pin_unique (pin_hash) WHERE consumed_at IS NULL AND revoked_at IS NULL`** = the lookup key of `POST /api/child/pin-login`; generation retries on a collision (savepoint) and revokes expired-but-open rows with the same hash first. A new PIN for a child revokes that child's open one. Old rows are not pruned yet (debt). The legacy parent-row PIN (`users.pairing_pin`, `POST /api/child/pair`) is separate.

**personal_access_tokens** (Sanctum) — every token issued since M2-02 has exactly one ability: `["parent"]` or `["child"]` (`TokenAbility::forUser`); tokens from before have `["*"]` and keep working. A child keeps at most **3** tokens (devices): each PIN login deletes the oldest beyond 3.

**device_push_tokens** (M3-02) — one row per app install that may receive Expo pushes: `id, user_id → users (cascade), personal_access_token_id → personal_access_tokens (nullable, **cascade**: the Sanctum token that registered it — logout, "sign out all devices" and pruning a child's 4th device drop the push registration with it), expo_push_token (unique, `ExponentPushToken[…]`), platform (ios|android, CHECK), app_version (≤ 32, e.g. `1.10.4 (abc1234)`), locale (M1-18, nullable ≤ 8: `en` \| `sl` — the install's push language, set only from the explicit `locale` body field of `POST /api/devices`; rows from before M1-18 backfilled `sl`, new rows without the field also `sl` (`locales.unstated_device`); no CHECK so a new language stays a config change; null only as a safety net → English), last_seen_at, disabled_at, disabled_reason (`DeviceNotRegistered`), timestamps`. No device name / model (child data minimisation). Re-registering the same token from another account **moves** the row (`PushDeviceService::register`, `INSERT … ON CONFLICT`); registering again re-enables a disabled row.
**push_notifications** (M3-02) — one row per escalation push decision: `id, idempotency_key (uuid, unique), pet_id → pets (cascade), type (soft_warning|critical_alert|walk_reminder|parent_intervention_alarm|illness_triggered|game_over_virtual_shelter|trial_ending|payment_required (M3-11), CHECK), metric (hunger|thirst|hygiene|energy; illness: hygiene|walk), recipients (jsonb `[{user_id, audience: child|parent}]` — ids only), status (scheduled|queued|sent|suppressed|failed, CHECK), send_after (held rows), suppressed_reason (quiet_hours|duplicate|no_recipients|no_devices|pet_locked|walk_done|walk_day_over), attempts, sent_at, last_error, timestamps`. The duplicate guard reads it (same pet + type, queued/sent, within `PUSH_DEDUPE_MINUTES`); `push:receipts` deletes rows older than 30 days.
**push_tickets** (M3-02) — Expo's answer per (notification, device), **unique** on the pair (a retried send skips devices that already have a ticket): `ticket_id, status (ok|error), error, receipt_status, receipt_error, receipt_checked_at`. Cascade with the notification and the device.

**purchase_events** (M3-08) — the RevenueCat webhook ledger, one row per RevenueCat event: `id, event_id (string(128), **unique** — RevenueCat `event.id`, idempotency), type, app_user_id, original_app_user_id, aliases (jsonb), product_id, entitlement_ids (jsonb), store, environment (SANDBOX|PRODUCTION, CHECK), transaction_id, original_transaction_id, purchased_at / expiration_at / event_at (from the `*_ms` fields, UTC), family_id → families (nullable, **null on delete** — the ledger outlives a deleted family as a financial record), payload (jsonb, the whole body **without** `event.subscriber_attributes`), outcome (granted|revoked|transferred|recorded|ignored|unknown_user|sandbox_ignored|unknown_product, CHECK — `PurchaseEventOutcome`), processed_at, timestamps`. Written only by `RevenueCatWebhookService`; Filament "Payments → Purchase events" (read only).

**challenge_credits** (M3-11, replaces the never-deployed M3-08 `family_entitlements` — PAYMENTS_SPEC P1: one purchase = one 12-week challenge for one pet) — `id, family_id → families (**cascade**), purchase_event_id → purchase_events (**unique**: one credit per purchase), product_id, store, environment (CHECK), transaction_id (indexed — refunds match on it), purchased_at, pet_id → pets (nullable, **null on delete**: a deleted pet's credit stays used), assigned_at, assigned_via (parent|webhook|birth — `birth` = a held credit paid the pet at its contract, M3-13, migration `2026_10_23_130000`; CHECK: all three null = available, else assigned_at + via set), revoked_at, revoke_reason (refund, CHECK: set iff revoked), revoke_event_id, transferred_at, transferred_from_family_id, timestamps`. **Partial unique index** `challenge_credits_one_per_pet (pet_id) WHERE revoked_at IS NULL AND pet_id IS NOT NULL`. Available = not revoked and `assigned_at` null. Written only by `ChallengeCreditService` (webhook and `POST …/challenge/activate`; lock order family row → pet row → credit rows). Filament "Payments → Challenge credits" (read only).

Laravel default tables: `password_reset_tokens, sessions, cache, jobs, failed_jobs, personal_access_tokens`.

## 4. Game loop

`routes/console.php` schedules `pets:process-decay` every minute (`withoutOverlapping`, `runInBackground`) → **M3-11 first `ChallengeService::processTrials()`** (unpaid, born, active challenge pets: `trial_ends_at` ≤ now → payment lock under the row lock — non-quiet save, so the `Pet` hooks stamp `frozen_at` and open a `payment_lock` status period; one `PetUpdated('payment_required')`; one `payment_required` push to parents + caretakers; no `trial_ending` reminder since M3-13. Also daily at 03:17 UTC: `pins:prune` (M2-02) deletes `child_login_pins` rows whose PIN expired more than 7 days ago (`--days=N`; every PIN expires 15 min after issue, so this covers used, revoked and unused ones).

**PetDecayService** (M1-01/M1-02, scheduler selects IDs of active, non-game-over pets): decay is a pure function of (precise stored metrics, elapsed time `last_decay_at → now`, breed config, quiet hours). `updated_at` is never used, so other writes don't eat decay; missed ticks are caught up in full (no cap).
- **Concurrency:** each pet is processed in its own `DB::transaction` from a fresh `Pet::lockForUpdate()` read (the passed model is only an ID and is synced afterwards), so a concurrent write is never overwritten by a stale copy. Other metric writers must take the same lock (`backend/CLAUDE.md`; `EditPet` does).
- First tick with `last_decay_at = null` only starts the clock.
- **Unborn pets** (`born_at` null, M1-07b) are excluded in SQL (`Pet::born()` scope) from both the decay tick and escalation, and `decayLockedPet` / `escalateLockedPet` / `DailyWalkService::closeDayIfNeeded` / `HygieneEventService::ensureScheduled|applyDue` return early for them as a second guard: no decay, no hygiene schedule, no day close, no escalation, nothing written. `Pet::giveBirth()` (called by `signContract` under the row lock) starts every clock at the signing moment; events of the birth day before that moment are skipped like any pre-birth event.
- **Frozen** while `is_hard_stopped`, **payment-locked (`payment_locked_at`, M3-11 — the same mechanism as the hard stop: `Pet::isFrozen()`; lifting it on payment runs `applyThaw()`, shifting every `*_zero_since` by the locked time and restarting the decay clock; behaviour / bladder clock held; training sessions interrupted and routines excused through the `payment_lock` status period)**, ill (`illness_until` in the future), inactive or game over: metrics untouched, `last_decay_at` advanced to now (quiet write). Hard stop / payment lock / illness also stamp `frozen_at`. The local midnight still closes the day while hard-stopped / ill (walk row, steps → 0) but never schedules a walk illness, and a walk illness that comes due during a freeze is dropped.
- **Illness recovery = fresh start** (David 2026-10-03, `Pet::recoverFromIllnessIfDue()`; first thing in every decay tick, escalation tick, child action and model update once `illness_until` has passed): at `illness_until` → hygiene 100 % and `hygiene_zero_since` null (the vet cleaned the dog), every other running `*_zero_since` restarts at `illness_until`, `escalation_level` 0, `illness_until` null, decay clock resumes at `illness_until`. Hunger / thirst keep their values. If a hard stop or the payment lock (M3-11) is still on, `frozen_at` = `illness_until` (the freeze continues). One `PetUpdated('metric_changed')` after commit. Fixes the illness loop (before, the clock still showed ≥ 6 h after the 12 h).
- **Thaw of a hard stop** (`Pet::applyThaw($at)`): shifts every non-null `*_zero_since` forward by `at − frozen_at` (neglect time spent frozen doesn't count), restarts the decay clock at `at`, clears `frozen_at`. `at` = now when a hard stop is lifted (`updating` hook — works without any tick during the freeze). Re-activation / undoing game over restarts the decay clock.

- Verified by 24 h minute-by-minute simulations (`tests/Feature/PetDecayTest.php`): mutt hunger 0 % at exactly 750 min, thirst 600 min; BC hunger 500 min, thirst 400 min; hygiene 91 after 6 h. Identical with 5-min ticks or a 3 h scheduler gap.
- Verified 24 h simulations with events enabled (mutt + BC): hunger/thirst zero minutes unchanged (750/600, 500/400), hygiene 100 % until an applied event and 0 % after, energy 0 % at minute 900 (local midnight).
- `pet_state`: `sick` only for hygiene 0 % (and during illness); energy 0 % shows `low_energy` outside quiet hours (`sleeping` inside).
⚠️ Remaining: hunger/thirst `*_zero_since` set at tick time (not the exact crossing time) after a catch-up gap.

**PetActivityService** (M1-04/M1-05/M1-07; called by `ChildPetController` / `ChildContractController`). Each action: transaction + `lockForUpdate()`, illness recovery first if due, refused with `ActionResult::LOCKED` + `PetLockReason` while game over / inactive / hard-stopped / unborn (`contract_required`) / ill, quiet write, one `activities_log` row (created without model events), one `PetUpdated(<activity type>)` after commit. A refused or unchanged action still broadcasts one `PetUpdated('metric_changed')` if its bookkeeping (recovery, midnight, decay catch-up) changed what the child sees.
- `feed(Pet)` / `water(Pet)` (M1-07): first `PetDecayService::catchUpLocked()` — one tick under the same lock, no broadcast — so decay owed since the last tick lands on the old value, not on the new 100 %, and due hygiene events are seen. Hygiene showing 0 % → `REFUSED needs_cleaning` (PRODUCT_SPEC §8). Then `CareScheduleService` (feed windows / water limits, see below) → `REFUSED` with `next_allowed_at`, or hunger / thirst → 100 %, `*_zero_since` → null, `pet_state` re-derived (`PetDecayService::derivePetState`), `fed_pet` / `watered_pet` row with the value shown before.
- `signContract(Pet, child, format, signature)` (M1-07): one `pet_contracts` row per **(pet, child)** since M2-01 (`REFUSED contract_already_signed` → 409 for the same child; the first contract births an unborn pet, later ones only unlock that child), `signed_contract` row, `PetUpdated('signed_contract')`. Passes only the `contract_required` lock. Unborn pet (M1-07b) → `Pet::giveBirth(now)` in the same transaction / row lock: `born_at`, `last_decay_at`, `last_step_reset_at` = signed_at, metrics 100, steps 0, neglect clocks / escalation / `walk_illness_due_at` / `hygiene_scheduled_through` / `frozen_at` cleared, `pet_state` derived; still one broadcast after commit. A grandfathered (born) pet only stores the contract.
- `clean()` now also re-derives `pet_state` (no `sick` video until the next tick).

**CareScheduleService** (M1-07): pure rules on top of `breed_configs` and `activities_log`, evaluated in the family timezone. Feed windows: the breed's `feed_windows` [start, end) "HH:MM" pairs instantiated for local yesterday…+2 days (an end ≤ start runs over midnight; a time in the spring-forward gap resolves to the instant after the jump; an empty / invalid config falls back to `BreedConfig::DEFAULT_FEED_WINDOWS`, single invalid windows are ignored; the warning is logged at most once per breed per UTC day via a cache key; Filament requires ≥ 1 window and rejects overlaps on save); "already fed" = a `fed_pet` row at or after the current window's start. Water: `watered_pet` rows in [local midnight, next local midnight) (23 h / 25 h on DST days) vs `water_times_per_day`; gap = real minutes since the latest `watered_pet` row (across midnight too); `next_allowed_at` = max(gap end, next local midnight) when the day's limit is reached.

**Life stages (M5-R01, `LifeStageService`, David 2026-10-05).** Rules of a family-local **day** follow the dog's age at the **start** of that day: `rulesOn(pet, date)` → `StageRules {ageMonths, lifeStage, mealsPerDay, feedWindows, exerciseMinutes, stepGoal, sleepHours, provenance}`. Stage = the last `starts_at_months` ≤ age (mutt: puppy 0, young 9, adult 36, senior 108; Border Collie senior 118). A stage key resolves to the row of the current stage with the greatest `age_from_months` ≤ age, else the breed-level row. Meals: puppy 4 (from 2 months) → 3 (from 3) → 2 (from 6); young / adult / senior 2. Windows belong to the meal band: the band's `feed_windows` row (4: 07–09, 11–13, 15–17, 19–21; 3: 07–09, 13–15, 19–21 — 2-hour windows, David 2026-10-05), else `breed_configs.feed_windows` when the count matches (2 meals: 06–10, 17–21), else N derived 2-h windows 07:00…19:00 (shorter when the spacing is shorter; logged). Step goal = exercise minutes × `steps_per_exercise_minute` (100): puppy / young minutes = 10 × age (contested S24 rule, confirmed by David 2026-10-05) capped at the adult minutes (mutt 60 — David decision, Border Collie 120 sourced), senior 75 % (David decision: mutt 45, Border Collie 90); then `daily_steps_cap`. `profile.data_verified` is true when every used row is verified (all seeded rows since 2026-10-05). Users: `CareScheduleService` (windows per day — `feeding()`, `feedWindowsStartingOn(pet, config, date)`), `PetActivityService::recordSteps` (energy = steps / today's goal), `DailyWalkService` (closed day's goal), `RoutineLedgerService` (feed routines per that day's windows, walk goal per day), `PetProfilePayload`. Without stage data for a breed — and always for a **legacy-profile pet** (`arrival_age_months` null) — every rule falls back to the pre-M5 breed config and `life_stage` is null. `data_verified` also requires the provenance of the current stage's `starts_at_months` and of the arrival age (Claude's boundary / arrival choices are `verified = false` until David confirms).
- **Transition:** the decay tick calls `syncStage()` under the row lock and writes `pets.life_stage` (never for a legacy-profile pet); a **forward** change between two known stages queues **one** `RegeneratePetStageMedia` after commit (a backward change — an admin moved a boundary — only updates the stage, no images; `startStageTransition` also refuses to grow an image backward). A lost / given-up stage job is re-queued by `media:retry` (daily) and `media:backfill` (`planMissing` image action `stage`) when the stored image shows an earlier stage than the pet; a stage image that failed on the budget (slot still pointing at the archived file) is retried like a missing image (`ReferenceImageRetryService::canRetry` ignores archived files). Rules change only at a family-local midnight (`rulesOn` uses the age at the start of the day), so a transition never rewrites the current day; closed days (`pet_daily_routines`, `pet_daily_walks`) are never recomputed. Parent-covered meals after a scheduler outage: hunger decays piecewise (to the meal, 100 %, on to now), identical to real-time ticks. **Known limitation:** a quiet-hours edit applies retroactively to the not-yet-ticked interval and to live (not yet closed) days — which windows count as parent-covered is decided with the current quiet hours (the lock makes it once; the job is unique per pet). The broadcast of that tick carries the new stage. The 12-week puppy challenge (arrival 2 months) moves puppy → young in week 8 (age 9).
- **Meals in quiet hours (done by the parent):** a window that lies **entirely** in quiet hours (`CareScheduleService::isParentCovered`) is never a child routine (ledger skips it, as before); the decay tick (`dueParentMeals`: windows that started in (`last_decay_at`, now], after birth, not fed yet) sets hunger to 100 % and writes one `parent_fed_pet` row at the window start. Frozen pets (hard stop / vet / inactive / game over) are not fed by the tick. A window only partly in quiet hours stays the child's.
- **Actor (M2-01):** `feed/water/clean(Pet, ?User $actor)`, `recordSteps(…, ?User $actor)`, `signContract(Pet, $child, …)` — the lock is evaluated for the actor (`actionLockReasonFor`), the activity row stores `actor_user_id`; no actor (system / old callers) = the primary caretaker (`pets.user_id`). Feed windows and water limits stay **per pet** (the dog is fed once per window, whoever feeds it).
- `recordSteps(Pet, int $stepsToday, Carbon $recordedAt, ?User $actor)`: **per child** since M2-01 — `$stepsToday` is the acting child's own cumulative count in `pet_daily_steps` (idempotency and the anti-cheat reference `last_sync_at` per child); the accepted increment is added to the pet's `daily_step_count` (sum of all caretakers = the daily walk); the `walked_pet` row goes to the child whose sync crossed the goal. For one child this is identical to before: cumulative count for the family-local day, the max wins (`UNCHANGED` for repeats / lower counts). Anti-cheat: increment capped at 200 steps per minute between max(`last_step_sync_at`, local midnight) and `recordedAt` (future → now) — `CAPPED` keeps the plausible part, `REJECTED` if none; a sync dated on an earlier local day is `STALE`. Closes the previous day first (`DailyWalkService`, same as the tick). Energy = max(current, min(100, steps / `daily_steps_required` × 100)). Logs one `walked_pet` row per day, when the count first reaches the goal (value = steps). If the action itself changed nothing but closed the previous day or applied a recovery, it still broadcasts one `PetUpdated('metric_changed')` after commit.
- `clean(Pet)`: catches up decay (`catchUpLocked`, since M5-R02 — due messes incl. accidents happen first), settles hygiene events already due but not yet ticked (`HygieneEventService::settleForCleaning`), stamps `cleaned_at` on open **poop / accident** events, hygiene → 100 and `hygiene_zero_since` → null **only when no mess of any kind is left open** (an open chewing event keeps hygiene at 0), logs `cleaned_poop`. `UNCHANGED` when there is nothing the cleaning game resolves.
- `resolveChewing(Pet, ?User)` (M5-R02): catch-up, `settleChewing` (open chewing → `cleaned_at`), hygiene 100 % if nothing else is open, `resolved_chewing` row. `UNCHANGED` when nothing is chewed.
- `takeOut(Pet, ?User)` (M5-R02): catch-up (a due accident happens first), `REFUSED take_out_not_needed` when `BehaviourEventService::pottyClock()` is null (behaviour events off, not a puppy, unborn — exactly when the payload's `behaviour.take_out` is null, PR #42 m2), `UNCHANGED` if a `took_out_pet` row of this pet is < 60 s old, else `pets.potty_clock_started_at` = now + `took_out_pet` row.

**EscalationService**: same row-lock rule as the decay tick (M1-07 review fix): the scheduler selects IDs only and each pet is re-read with `lockForUpdate()` in its own transaction; every decision uses that fresh row, so a clean / feed / hard stop committed after the scheduler's query is respected (before, a stale model could start an illness or a game over the child had just prevented). `processPetEscalation(Pet)` uses the model only for its ID and copies the result back. Each step taken emits exactly one `PetUpdated` after commit (M1-08): `soft_warning` (level 1), `critical_alert` (level 2), `parent_intervention_alarm` (level 3), `illness_triggered`, `game_over_virtual_shelter`, `escalation_reset` (metrics recovered → level 0). A tick takes at most one step per pet; no step → no event. Skips hard-stopped and ill pets entirely (M1-02 — no new escalation, illness or game over while frozen; `thawIfDue()` runs first: recovery of an expired illness, stale `frozen_at`). Neglect clocks = hunger, thirst, hygiene (**not energy**). Then: game over (hunger / thirst / hygiene 0 % ≥ 24 h → `is_active=false`, `is_game_over=true`) › illness — (a) `walk_illness_due_at` ≤ now → illness from `walk_illness_due_at` (`illness_until` = due + 12 h, `frozen_at` = due, walk row `illness_started_at`); if due + 12 h ≤ now (scheduler down) it is skipped instead (walk row `illness_skipped_at`, no recovery side effects); game over and reactivation clear a pending `walk_illness_due_at`, or (b) hygiene 0 % for ≥ 6 h **counted outside quiet hours only** (`QuietHours::splitSecondsBetween(zero_since, now)['normal']`) → `illness_until = now+12h`; state `sick`, `frozen_at` = start › matrix (lowest displayed **hunger / thirst / hygiene** ≤ 30 → level 1, ≤ 10 → level 2; 0 % ≥ 1 h → level 3). **Energy is not on the ladder** (PR #35 re-review): after the matrix, energy showing ≤ 30 % outside quiet hours calls `NotificationService::walkReminder()` (no level, no activity row, no broadcast); `pet_state` `low_energy` is unchanged (decay tick). The deprecated top-level `traffic_light` is therefore no longer amber for energy alone. Each escalation writes an `ignored_warning` activity (`actor_user_id` null). Push jobs are commented out (none exist); recipients are resolved in one place (M2-01): `FamilyService::caretakerRecipients($pet)` (phase 1 / 2 → every caretaker child) and `FamilyService::parentRecipients($pet)` (phase 3, illness, game over → **every parent of the family**); their ids are logged with the escalation.

**Routine ledger / Care Score / traffic light (M2-06, David 2026-10-04, PRODUCT_SPEC §9/§11).** `RoutineLedgerService` derives the routines of each family-local day from existing data (no new client calls): **feed** = each breed feed window starting that day (`CareScheduleService::feedWindowsStartingOn`, same window rules as the child API; done = a `fed_pet` row in [start, end); a window entirely inside quiet hours is not expected); **water** = `round_half_up(water_times_per_day × in-play non-quiet seconds / non-quiet seconds of the day)` refills (birth, hard stop, vet, game over pro-rated), done = that day's `watered_pet` rows in order, the rest missed at day end; **clean** = each `applied` hygiene event — poop, puppy accident or chewing (M5-R02, `Routine::eventKind` / `pet_daily_routines.event_kind`; actor = the `cleaned_poop` row, for chewing the `resolved_chewing` row, written with `cleaned_at`), done when `cleaned_at` ≤ event + 2 h counted outside quiet hours (`addSecondsOutsideQuiet`; actor = the `cleaned_poop` row of the same action, ±5 s); **walk** = the day's goal (`pet_daily_walks`, live `daily_step_count` for the pet's current step day, else the children's `pet_daily_steps`), not on the birth day, not for a past day without step data; done = goal reached (actor = the `walked_pet` row); **training** (M5-R03) = one completed session a day for a pet with training enabled, not on the birth day, done = the day's first `trained_pet` row (actor = that child; fair share like feed), excused like the walk (whole-day routine). Order of resolution: done › excused (window overlaps a `pet_status_periods` row and not done → not expected; **the walk — a whole-day routine — only when those periods cover ≥ 50 % of the day's non-quiet time**, `WHOLE_DAY_EXCUSE_SHARE`, so a short or overnight hard stop doesn't excuse it; water is pro-rated instead) › pending (deadline ahead) › missed. A hygiene event still `pending` inside a status period (e.g. after game over — the tick never processes it) is ignored, so it can't keep the day open. Join day: a caretaker who signs mid-day doesn't share that day's water / walk (they open at the day start). Unborn pets and days before `FIRST_LEDGER_DATE` (2026-10-04) have none. Wall clock = family tz, DST-safe (days of 23 / 25 h, instants UTC).
- **Materialisation:** `closeDueDays()` (end of every tick) selects at most `MAX_PETS_PER_TICK` (500) born pets with `routines_next_close_at ≤ now` (or never closed; never-closed and longest-overdue first), computes the days after `routines_closed_through` up to local yesterday (≤ 120 per pass — the backfill of existing pets happens in slices on the first ticks after deploy), stops at the first day that is not final (a pending routine — e.g. a 21:30 mess due 07:30 next morning — or a hygiene event still `pending`), inserts the final days' rows (`insertOrIgnore`) and moves the pointer in one transaction under a `FOR UPDATE` lock on the pet row, only if `routines_closed_through` and `routines_next_close_at` are still the values it read (a concurrent re-activation wins; retried next tick); `routines_next_close_at` = the pending deadline, else the next local midnight; null for an inactive pet whose last closed day was empty (re-activation resets it). A failure for one pet is logged, never stops the tick and pushes that pet's `routines_next_close_at` 30 min ahead (no log flood). Reading (`routinesFor`) = stored rows for closed days + the same computation live for the rest (today), in a constant number of queries for any number of pets and days.
- **Scoring (`CareScoreService`):** pet score = done / expected × 100 − 10 × illnesses (`pet_status_periods` kind illness), clamped 0–100, rounded half up; child score = min(100, done_by_child / fair_expected × 100) − 10 × illnesses since the child started; fair_expected = Σ 1/n over the routines the child shares (n = caretakers whose start ≤ `opens_at`; start = own contract `signed_at`, or `born_at` for grandfathered caretakers); done_by_child = routines whose actor is the child, walk = goal met and the child's steps ≥ goal / n (n = 1 → goal met). Pending routines are not scored; no expected routine → score null; illnesses count from the first ledger day (and the child's start). Traffic light (today, family-local): red = game over › phase 3 (escalation 3) + "fell ill today" (illness period started today); else yellow = > 2 missed routines of today — today's date **or a deadline in (today 00:00, tomorrow 00:00]** (`todayRoutines`, also used by the `today` block) — per child every missed routine they shared; else green. `FamilyDashboardService::family()` builds one board per family (`CareScoreService::board()`), `childReport()` the report.

**Push notifications (M3-02, `NotificationService`).** Every escalation step of `EscalationService` (same per-pet transaction, pet row locked) calls `NotificationService::escalation($pet, PushType, $metric)` once, next to its `PetUpdated::afterCommit`:
- **Recipients** — only through `FamilyService`: phase 1 `soft_warning` / phase 2 `critical_alert` → `caretakerRecipients()` (active caretaker children); phase 3 `parent_intervention_alarm` → `parentRecipients()` (every parent); `illness_triggered` / `game_over_virtual_shelter` → parents + caretakers (each audience its own text). `escalation_reset` sends nothing.
- **Metric for the text:** phase 1 / 2 = the lowest displayed of hunger / thirst / hygiene (ties in that order); phase 3 = the first of hunger / thirst / hygiene at 0 % ≥ 1 h; illness = `hygiene` or `walk` (missed daily walk).
- **Walk reminder (PR #35, Claude, čaka Davida):** separate from the ladder — `NotificationService::walkReminder($pet)` (called by escalation each tick while energy shows ≤ 30 % outside quiet hours) creates a `walk_reminder` only if **no walk_reminder row exists for this family-local day** (any status — a dropped one isn't retried every minute); normal priority, channel `default`, not before `PushTiming::walkReminderEarliest()` = 2 h after the quiet stretch running now, else 2 h after the day's last quiet stretch, else now (bedtime → 06:00 → 08:00; school 08–13 → 15:00) — and never before `PushTiming::walkReminderFloor()` (David 2026-10-08 08:54): 2 h after the **stored** night window end (bedtime that wraps midnight; 21:00–07:00 → 09:00) **also when quiet hours are switched off** (a night window = bedtime that wraps midnight, or starts 00:00–`NIGHT_START_LATEST` 04:00 without wrapping: 00:00–06:00 → 08:00), else `WALK_FLOOR_FALLBACK` 09:00 local, so the midnight energy reset never sends a reminder at 00:00. Too early → row `scheduled` with `send_after`; dropped (`walk_day_over`) if that time is on another local day; dropped at send time (`walk_done`) if energy shows > 30 %.
- **Play reminder (M5-R06-04, cats):** `NotificationService::playReminder($pet)` — the walk reminder's twin for a cat's play meter (`PushType::PlayReminder`, metric `play`, `isDailyReminder()`): one decision per family-local day, the walk-reminder floor, recipients = caretakers, normal priority. At send time: meter > 30 % → `suppressed play_done`; a refusal that ends later today (another child's game, the 2 h gap) → held (`scheduled`, `send_after` = its end); any other refusal (mess, …) → `suppressed not_actionable` (M3-12), which does not count as "decided today" (QA). - **Litter reminder (M5-R06-05, cats):** `EscalationService` → `NotificationService::litterReminder($pet)` outside quiet hours when an unscooped litter use has ≤ 60 min of its outside-quiet deadline budget left (so a deadline moved past the night — 17:00 use → 07:00 — is reminded at 20:00, before quiet hours; QA m2) (`PushType::LitterReminder`, metric `litter:{use id}`, caretaker children, normal priority, TTL 1 h); exactly once per litter use (no 30-min type dedupe). Copy `push.litter_reminder` / `push.scratcher.*` / `push.clean_and_scratcher.*` (EN + SL) are **placeholders** until M5-R06-06.

- **Stuck rows:** `push:dispatch-scheduled` also re-queues rows `queued` with `attempts = 0` untouched for `STUCK_MINUTES` (20, > the job's 15-min unique lock); if queueing throws, a claimed row goes back to `scheduled` (due now).

## 5. Real-time

**Channel (M1-08).** Reverb (`BROADCAST_CONNECTION=reverb`), one event `PetUpdated` (`broadcastAs: pet.updated` — Echo listens to `.pet.updated`) on **`PrivateChannel('pet.{id}')`**, wire name `private-pet.{id}`. No public channels exist.
- **Who may subscribe** (`routes/channels.php` → `PetPolicy@listen`, family model M2-01): **every caretaker child** of the pet (`pet_caretakers`) and **every parent of the pet's family** (`family_user`). A sibling who cares for another pet, a parent or child of another family, a guest, a missing or malformed id → denied. The old `pet.updated.{id}` channel is gone.
- **Auth endpoint:** `POST /api/broadcasting/auth` with `Authorization: Bearer <sanctum token>`, body `socket_id`, `channel_name` (§3). pusher-js calls it on every subscribe through the app's `channelAuthorization.customHandler`.

**Exactly one event per state change.** The single emission point is `PetUpdated::afterCommit($pet, $eventType)`, called by the service that made the change (decay tick, `PetActivityService`, `EscalationService`, hard stop, Filament `EditPet`, fal.ai webhook / job, RevenueCat webhook). There are **no model observers** (`PetObserver` / `ActivityLogObserver` removed): a plain `Pet::save()` or `ActivityLog::create()` broadcasts nothing. Why: the services know which change is meaningful and its type; observers fired on every save, duplicated explicit calls (escalation sent up to 3 events per step) and couldn't name the change. A decay tick that also crosses an escalation threshold sends two events (two state changes: `metric_changed`, then e.g. `soft_warning`).

**Queued, after commit, never fatal (M1-09).**
- `afterCommit` defers to `DB::afterCommit` (and the event also implements `ShouldDispatchAfterCommit`): a rolled-back transaction broadcasts nothing; the snapshot shows committed state.
- `PetUpdated` is `ShouldBroadcast` (not `ShouldBroadcastNow`) with `broadcastQueue = 'broadcasts'`; tries 3, backoff 2 s, timeout 15 s. The tick / request only pushes a `BroadcastEvent` job; the worker talks to Reverb. The job holds no model (snapshot payload), so a deleted pet can't fail it.
- `afterCommit` catches any exception from queueing/broadcasting (logs `PetUpdated: broadcast could not be queued` + `report()`), so a queue or Reverb outage never stops `pets:process-decay` for the remaining pets and never turns a committed child action into a 500.
- Production: dedicated worker `queue-broadcasts` (`queue:work redis --queue=broadcasts`) next to `queue` (`--queue=default`, fal.ai) in `compose.production.yaml` — a slow fal.ai job never delays a broadcast and a Reverb outage never blocks fal.ai. Locally (`QUEUE_CONNECTION=sync`/`database`) run `npm run sail:queue` or the job runs inline.

**Mobile** (`usePetWebSocket` + `src/modules/realtime/echoConfig.ts`): laravel-echo `reverb` with a pusher-js client — `wss` on `EXPO_PUBLIC_REVERB_PORT` (443) with `forceTLS` when the scheme is `https`, `ws` only for local http; `enabledTransports` is **always `['ws', 'wss']`** (with TLS pusher-js 8 only uses the transport *named* `ws`, over `wss://` — `['wss']` alone disabled every transport → `failed`, fixed 2026-10-05); the constructor comes from `resolvePusherConstructor()` because Metro bundles pusher-js' React Native build, which exports `{ Pusher }` without a default (the old `.default` shim threw → permanent `disconnected`, fixed 2026-10-05; regression tests run the real RN build in `pusherReactNative.test.ts`); `echo.private('pet.{id}')`; authorizer = `api.authorizeChannel()` (Bearer token read fresh each subscribe, 401 → session logout handler). `wsStatus` is `connected` only after the channel subscription succeeds (`channel.subscribed`); a subscription error / `unavailable` → `reconnecting`, `disconnected` / `failed` → `disconnected`. The hook drops any event whose `emitted_at` is older than the last one delivered (`createBroadcastGate`) and hands events to a handler: **child HUD** → `applyBroadcastToCache` (TanStack cache `['child','pet']`, M1-13), **parent app (M2-05, PR #20 review)** → `ParentLiveChannels` → `usePetChannels(petIds, handler)`: **one Echo (one websocket) with one private channel per family pet** that is active and not game over, an ordering gate per pet, and a **status per pet**; the store's `wsStatus` is `connected` only while **every** pet channel is subscribed (`aggregateChannelStatus` — one channel failing with 403 keeps polling on even if the others are live). Events go to `modules/family/live.ts#createParentBroadcastHandler`: the event's metrics / flags are patched into that pet of the cached `['parent','dashboard']` at once; any event other than `metric_changed` also invalidates the dashboard, `['parent','activities',petId]` and every `['parent','childReport',…]` (routines, Care Score, light and timeline are server computations); a `metric_changed` tick refetches the dashboard at most once per 60 s (a tick can close a window → missed). The session store is not touched by parent events (`updatePetFromBroadcast` is only the no-handler fallback of `usePetWebSocket`). **Polling:** `useChildPet` refetches `GET /api/child/pet` every 10 s (M1-15) while not connected; `useParentDashboard` every **30 s** while not every pet channel is live, and every **3 min** while live (feed windows / deadlines pass without any event) — both paused in the background via `focusManager`.
- **Ordering on the child:** the cached view remembers `server_time` of the last HTTP snapshot (whole seconds) and `emitted_at` of the last applied broadcast (ms). A broadcast older than either is dropped; a poll that hasn't seen the newest broadcast is dropped when its `server_time` is from an earlier second (`mergePolledState`, run as TanStack `structuralSharing`); action responses always win. A broadcast can't describe feed windows / water / the per-child contract flag, so any event other than `metric_changed`, or one that changes the lock or the mess flag, also triggers a background refetch. The broadcast's pet-level `awaiting_contract: false` never clears the child's own contract flag. A tick that lowers `energy_level` (the family midnight reset) also refetches. A poll older than the shown HTTP snapshot is dropped too.
- **Time-based refresh (PR #18, M3):** no event announces that a feed window opened, the water gap ended or the family day changed, so `useChildPet` keeps one timer for the earliest of `feeding.next_feed_window.start`, `feeding.current_window.end`, `water.next_allowed_at` and the next family midnight (`familyCalendar`), +1 s, then `invalidateQueries(['child','pet'])`; rescheduled on every new state, cleared on unmount. This runs also while the socket is live (polling doesn't). Boundaries are compared in **server time**: each HTTP state stores `clockSkewMs` = `server_time` − device clock on arrival (`nextRefreshDelay`). If a boundary has passed but the state still blocks the action (not because of a lock or mess), it retries every 30 s. Since the 2026-10-06 hotfix the end of a vet visit (`lock.until` while `lock.reason = ill`) is a boundary too.
- **Refetch limits (hotfix 2026-10-06, `modules/childPet/refetchGovernor.ts`; TestFlight 1.24.4: `GET /api/child/pet` → 429 from `throttle:api` = 60/min **per user, shared by every `/api/*` route incl. `POST /api/broadcasting/auth`**):**
  1. **Fetch gate** — every `GET /api/child/pet` (boundary timer, 10 s polling, broadcast / push / media-expiry invalidation, focus, retries, the retry button) goes through `childPetFetchGate`: token bucket, burst 3, then 1 per 6 s (≤ 10/min sustained). A 429 closes it until `Retry-After` (default 30 s, max 5 min). `POST /api/broadcasting/auth` has its own gate (`channelAuthGate`, burst 6, 1 per 10 s) so a pusher-js reconnect storm can't drain the per-user limit. Both reset on logout.
  2. **Boundary backoff** — the boundary timer fires at most once per 30 s; while consecutive boundary refetches bring no change (`viewSignature`: everything but clocks and re-signed media URLs) the gap doubles to 60 s, 120 s, 240 s, max 5 min.
  3. **Retries** — the child query retries 429 / 5xx / network errors twice (`Retry-After`, else 2 s, 4 s), never other 4xx; the cached view stays on screen meanwhile. Once the query is in the error state the hook retries by itself (`Retry-After`, else 15 s, 30 s, 60 s, 120 s) — with a cached view the HUD shows the "stale" banner, without one the error screen says "Poskušam znova samodejno …". The global `queryClient` uses the same `retryDelayFor`.
- **Push registration (hotfix 2026-10-06, the incident's root cause):** on iOS every `getExpoPushTokenAsync()` re-emits `onDevicePushToken` (expo-notifications `PushTokenModule.swift#didRegister`), so the token listener must never call `registerForPush()` directly — it calls `handlePushTokenEvent(deviceToken)` (ignores the echo during / 10 s after our own fetch and unchanged tokens). `registerForPush()` shares one in-flight run, sends each (session token, Expo token) once per app run, `POST /api/devices` is limited by `devicesGate` (2, then 1/min) and retries with `Retry-After` / backoff, max 3 attempts; reset on logout. The old listener looped at network speed (Caddy: up to ~1 700 `POST /api/devices` per minute) and drained the shared `throttle:api` bucket.
- **HUD error boundary:** `AppNavigator` wraps `ChildHudScreen` in `components/HudErrorBoundary.tsx` (dark card "Ups, nekaj se je zataknilo" + "Poskusi znova" → remount, cache kept). Exceptions thrown from native callbacks outside React are still fatal.
- **Lock overlay before the state loads:** the family zone is remembered on the device (`modules/session/familyTimezone.ts`, SecureStore `petprep.family_timezone`, written from each child state, read on restore, deleted on logout); `LockedScreen` formats `until` in that zone, else the device zone (`deviceTimeZone()`), else the device's local clock — never the UTC wall clock of `/api/user`'s `illness_until`.

## 9. Production

**Runtime (M4-05b, DEPLOYMENT.md D14):** production image `backend/docker/production/Dockerfile` — `php:8.3-fpm-bookworm` + extensions (pdo_pgsql, pgsql, redis, intl, zip, bcmath, gd, exif, pcntl, opcache), code + `composer install --no-dev --optimize-autoloader` baked in (no bind mount of the code; `composer.lock` changes reach production with the next deploy), non-root uid 1000 (`petprep`, same owner as the `app_storage` files of the Sail era). OPcache on with `validate_timestamps=0` (a deploy recreates the containers), realpath cache 4 MB, FPM `pm=dynamic`, `max_children=12`, `max_requests=500`, `request_terminate_timeout=65s`. `docker/production/entrypoint.sh` builds the Laravel caches **inside each container** on start (`app`: `php artisan optimize` = config, events, routes, views, Filament components + Blade icons; CLI containers: config + events), compiled views in `bootstrap/cache/views` (`VIEW_COMPILED_PATH`) — nothing cache-related on a shared volume any more. The same image runs `app` (php-fpm), `reverb`, `queue`, `queue-broadcasts`, `scheduler`; Caddy runs target `web` (caddy:2.8-alpine + `public/`) and serves `public/` itself (Filament css/js 30 days, `/build` 1 year immutable, zstd/gzip) and `php_fastcgi app:9000` for everything else (`REMOTE_ADDR` = the client Caddy sees, `HTTPS=on` → no proxy headers needed for the app). Fallback for local dev: Sail (`docker/8.5`, `php artisan serve`), unchanged.

Deploy (`scripts/deploy-production.sh`, since M2-01; images since M4-05b): env preflight (before any git/docker call) → record previous release (`repo/.deployed-sha`, tree snapshot in `/opt/petprep/releases/previous`) → **build `petprep-app:next` / `petprep-web:next` from the new tree + smoke test `php artisan optimize` — before maintenance, a failure changes nothing** → **`artisan down`** on the old code (maintenance file on the shared `app_storage` volume: HTTP 503, scheduler and queue workers pause) → DB backup → **code switch** (CI uploads to `/opt/petprep/incoming`, the script rsyncs it into the bind-mounted `repo/`; manual: `git checkout`) → images promoted (`:production` → `:previous`, `:next` → `:production`) → changed Caddyfile validated with the new caddy image (caddy recreated with `--force-recreate` after the migrations — single-file bind mount) → postgres/redis → migrate / seed → recreate containers (per-container caches) → wait for `php-fpm-ping` → `queue:restart` → **`artisan up`** (3 attempts) → health check `/up` end-to-end through Caddy (5 attempts) → prune dangling images. EXIT trap: failure **before** migrations succeeded → code **and images** reverted to the previous release, workers restarted, `artisan up`; failure **after** → release kept (new schema), containers restarted, `artisan up`, loud error. Harness: `scripts/tests/deploy-production.test.sh` (CI job `deploy-script-tests`).

See `docs/PRODUCTION_DEPLOYMENT.md`. Single Hetzner host, Docker Compose: Caddy (`petprep-web`: TLS, static files, pet media) → app (PHP-FPM 8.3, `petprep-app`) / reverb; queue (`default`: fal.ai, media downloads); queue-broadcasts (`broadcasts`: PetUpdated → Reverb, M1-09; then `notifications`: Expo pushes, M3-02); scheduler (`schedule:work`); postgres 18; redis. Live at `https://api.petprep.si`.

**One-off reset of all game data (D17, David 2026-10-08):** `php artisan petprep:reset-game-data` (`App\Services\GameDataResetService`, dry run by default) deletes every family / user except superadmins / pet and all their rows, payments, AI spend + AI Lab rows, sessions, cache, jobs, then the `pet_media` files, the redis queues and the cache; keeps superadmins (+ their tokens), `breed_configs`, `breed_stage_params`, `breed_stage_param_changes`, `migrations`. Every schema table must be listed as KEEP / PARTIAL / DELETE_ORDER — an unlisted table blocks the run. On the server only through `scripts/reset-game-data.sh` (ops lock shared with deploys, free-disk check, maintenance, workers stopped, DB + media backup first; exit 1 = nothing deleted, 2 = committed but cleanup failed) — runbook `docs/PRODUCTION_DEPLOYMENT.md` §6a. **Ops lock:** `deploy-production.sh` and the reset hold `flock /opt/petprep/.ops.lock` for their whole run (a deploy waits ≤ `DEPLOY_LOCK_WAIT` s).
