Pre-deploy DB backup, 7-day retention.

## SSH access from a new computer

The server only accepts keys. Add the new machine's public key from a computer that already has access:
```bash
# on the NEW computer
ls ~/.ssh/id_ed25519.pub || ssh-keygen -t ed25519 -C "david@datavallis.com"
cat ~/.ssh/id_ed25519.pub            # copy this line
# on the computer that ALREADY has access
ssh root@138.199.172.97 'cat >> ~/.ssh/authorized_keys' <<< 'ssh-ed25519 AAAA... david@new-mac'
# back on the NEW computer
ssh root@138.199.172.97 'hostname && docker ps --format "{{.Names}}: {{.Status}}"'
```
For deployments as `deploy@`, copy `~/.ssh/petprep_deploy_key` securely (e.g. AirDrop / password manager) or add the new public key to `/home/deploy/.ssh/authorized_keys` the same way.

## Pet media → object storage (M4-05, D23) — runbook (David)

Do it on a quiet evening; every step before 5 can be undone by doing nothing. Zero AI spend (step 5 pauses generation for a few minutes).

1. **Bucket + keys.** Hetzner Console → Object Storage → *Create bucket* in **fsn1** (same location as the server; e.g. `petprep-media`), visibility **private**. *Generate credentials* (S3 access key + secret, shown once → password manager). **Backup mirror (QA #374 M4): a second bucket in another location (e.g. `petprep-media-mirror` in `nbg1`) in a SEPARATE Hetzner Console project with its own credentials** — those go only into `/opt/petprep/backup.env` (read by the backup cron, never mounted into the app containers), so a leaked app key cannot delete the backup. Bucket versioning: optional extra (see SCALING.md §4); not needed for the backup.
2. **Env** (`/opt/petprep/.env`, `PRODUCTION_ENV.md`), still with the local disk:
   ```
   PET_MEDIA_S3_BUCKET=petprep-media
   PET_MEDIA_S3_KEY=<access key>
   PET_MEDIA_S3_SECRET=<secret>
   PET_MEDIA_S3_ENDPOINT=https://fsn1.your-objectstorage.com
   PET_MEDIA_S3_REGION=fsn1
   ```
   Leave `PET_MEDIA_DISK` unset. Deploy (Run workflow or the next daily run, 03:17) → `/admin/system-health` tile **Media storage** = *Local disk · Bucket petprep-media reachable* (a real HeadBucket; red / yellow = keys, endpoint or bucket name wrong). From now on deleting a pet also deletes its files in the bucket.
3. **Dry run** (on the server): `docker compose -p backend -f /opt/petprep/repo/backend/compose.production.yaml exec app php artisan media:move-to-object-storage --dry-run` — files, bytes, *DB paths on neither disk* (already broken before), *orphans* (local files no row points at; never copied). The command first proves the keys can write (put / read / delete of a probe object).
4. **Copy + verify** (inside `tmux`; resumable — re-run after any error): `… artisan media:move-to-object-storage` then `… artisan media:move-to-object-storage --verify` → `failed 0`, `mismatched` all `repaired`, exit 0. Nothing local is deleted.
5. **Switch (QA #374 M3 — no new files may land on the local disk in between):**
   1. **Pause AI generation:** `/admin → Feature switches` → state media + »School & game clips« **off**, and `/admin → AI budget` daily cap **0** (stops new reference images); then wait until the `default` queue is empty (`/admin/system-health` backlog `default: 0`) — or `docker compose … stop queue`.
   2. Final copy right before the deploy: `… artisan media:move-to-object-storage --verify` (exit 0).
   3. Add `PET_MEDIA_DISK=s3` to `/opt/petprep/.env` and deploy (the deploy preflight refuses `s3` without `PET_MEDIA_S3_BUCKET` / `_KEY` / `_SECRET`).
   4. Right after the deploy: `… artisan media:move-to-object-storage --verify` once more (must report `copied 0`).
   5. **Resume:** switches back on, AI budget back to its value (`docker compose … start queue` if stopped).
   6. Check: the tile says *Object storage · reachable*; with a signed `/api/media` URL from the parent dashboard: `curl -sI "<url>"` → `302` with `Location: https://petprep-media.fsn1.your-objectstorage.com/…`; `curl -sL -o /dev/null -w '%{http_code}\n' "<url>"` → `200`; `curl -sL -r 0-1 -o /dev/null -w '%{http_code}\n' "<url>"` → `206` (AVPlayer Range); `curl -sIL "<url>" | grep -i '^HTTP'` → `302` then `200` (HEAD is presigned as HeadObject). On a phone the pet video / image loads; one new AI clip (Regenerate in Pet → AI media) is stored and plays — fal fetches the start frame through the same redirect.
6. **Backup mirror:** add `MEDIA_MIRROR_S3_BUCKET` / `_KEY` / `_SECRET` (+ `_ENDPOINT` / `_REGION` if not `nbg1`) to `/opt/petprep/backup.env` (PRODUCTION_DEPLOYMENT.md §6b), run `backup-offsite.sh && backup-offsite.sh verify`. Without these keys the nightly run backs up the DB and then fails loudly.
7. **Rollback** (any time before step 8): remove `PET_MEDIA_DISK=s3` and deploy — the local files are still there (files created while on s3 exist only in the bucket: copy them back with `rclone copy` before rolling back, or regenerate). The bucket copies stay; deleting a pet keeps removing them there too while the bucket is configured.
8. **Later (after ≥ 1 week stable + one good mirror `verify`):** free the disk with `… artisan media:move-to-object-storage --verify --prune-local` (asks; deletes only the local copies verified in that run; orphans stay for a manual look).

## Mobile releases: OTA update or store build (M5-F10, David 2026-10-12)

The app has `expo-updates` with `runtimeVersion: { policy: "fingerprint" }` (`mobile/app.json`), update URL `https://u.expo.dev/<projectId>`, channels `production` / `preview` on the EAS build profiles (`mobile/eas.json`). The fingerprint is a hash of everything native: native modules and their config plugins, native `app.json` config, icons, splash, `eas.json`. `mobile/fingerprint.config.js` keeps the library's default skip for the `android` / `ios` package.json scripts (`expo prebuild` on the build server rewrites them to `expo run:*`; `sourceSkips` replaces the default, so it is listed explicitly — the second failed build on 2026-10-12) and skips the config's `extra` section (`app.config.ts` writes the commit SHA into `extra.gitSha` — otherwise every commit would be a new runtime) and `google-services.json` (on the EAS build server, not in CI — otherwise Android would never match; a Firebase project change needs a store build by hand). The script resolves with `EAS_BUILD_PROFILE=production` (APNs mode in `app.config.ts`), like the production build. Verified locally: two commits → the same runtime; with / without `google-services.json` → the same Android runtime. On the build server EAS stores the `GOOGLE_SERVICES_JSON` file env var outside the project under another name and the fingerprint hashes the file `android.googleServicesFile` points to, so `fingerprint.config.js` also ignores that path (first Android build failed on it, 2026-10-19).

**Who decides — automatically:** after a production deploy (since D18; before: after every green `CI & Deploy` run on `main` that changed `mobile/`), `.github/workflows/mobile-ota.yml` runs `scripts/mobile-ota.sh` per platform:
- a finished EAS production build with the same runtime version exists → **`eas update --channel production`** (JS / assets only) — phones download it on launch and use it on the next start (`checkAutomatically: ON_LOAD`, `fallbackToCacheTimeout: 0`); the script exports `EXPO_PUBLIC_GIT_COMMIT=<short HEAD>` first (JS only, not in the fingerprint), so the app's »Različica aplikacije« line (parent Nadzor, child settings) shows the same commit `docs/research/app-release.json` records — and the parent's »Preveri posodobitve« can fetch it and restart at once (2026-10-29, harness `scripts/tests/mobile-ota.test.sh`);
- no such build → **no OTA**, a "New store build needed" warning + job summary line → David makes a new EAS build and submits it (store builds stay manual — he owns versions).
An installed build only ever accepts updates for its own runtime version, so a wrong guess cannot crash a phone. **Website record:** when the production channel got the update on **at least one** platform (David 2026-10-25; before: both), the script outputs `released=true` + `platforms=<ios,android>` and the workflow commits `docs/research/app-release.json` + `breed-registry.json` to `main` (`chore(release): record OTA <sha> (<platforms>) … [skip ci]`); the website's `registry-sync.yml` picks the export up within the hour and deploys petprep.si. Only the head of `main` is published (a re-run of an old CI run is skipped).
