## 2. Pravila (tehnično, angleško za kodo)
- **Plan per pet:** `free` (mutt sandbox, forever) or `challenge` (12-week program). Chosen by the parent when creating the pet (dog picker): "Free mutt" or "12-week challenge — 49,99 €" (no free trial since M3-13). Border Collie (premium breeds) only with `challenge`, and **the challenge only with a premium breed** (M5-F03, David 2026-10-07): a new pet with an explicit `plan: challenge` and the mutt (or no breed / no profile → mutt) → 422 `challenge_requires_paid_breed`; an omitted plan (old builds) → `challenge` for a premium breed, `free` for the mutt; a PIN stored before M5-F03 with challenge + mutt (and the deprecated `/child/pair`) creates a free mutt (`PairingService::createPet`). Join / relogin never change the plan. *(**Upgrade, David 2026-11-10 — built 2026-11-11 (M6-U01), live since 2026-11-11 (deploy + OTA):** a born, active free pet (mutt or domestic cat, not a pre-M5 legacy-profile pet) is upgraded to the challenge with the same pet by `POST …/challenge/activate` or the webhook with a purchase intent — `pets.challenge_started_at` = purchase, the 12 weeks (child week, score, certificate, the pet's simulation end) run from the purchase, age / life stage stay on birth; refusals 422 `game_over` / `pet_not_born` / `legacy_profile` / `free_plan` (`FREE_PET_UPGRADE_SPEC.md` §5). "Mutt + challenge" at creation (M6-U02, built 2026-11-11, live since 2026-11-11 (deploy + OTA)): a parent build that declares the client feature `free_breed_challenge` (generate-pin `features`, and `features[]` on `GET /api/breeds` → the free breed is `challenge_allowed`) may send `plan: challenge` with the mutt / domestic cat — that pet is a normal unpaid challenge pet (`payment_required`, payment-locked at birth unless a held credit pays it, webhook / intent / activate exactly as for a paid breed; a refund → free plan like any refunded mutt). Only the PARENT's PIN features count (the child's device is irrelevant). Without the feature (every older build) M5-F03 is byte for byte unchanged: 422 `challenge_requires_paid_breed`, and a stored challenge + free breed becomes the free plan (`Pet::creating`, `PairingService::createPet` — `PairingService::allowsFreeBreedChallenge`). `defaultPlanFor` and `convertUnpaidMuttToFree` are unchanged.)*
- **Free plan:** breed mutt only; no "week N of 12", no challenge completion / certificate (M2-01d 🛠 2026-10-12: `ChallengeCertificateService` only looks at `plan = challenge` pets — CERTIFICATE_SPEC); parent dashboard history limited to 7 days; basic media tier (static video set). Everything else (needs, actions, steps, escalation, illness, game over, hard stop, quiet hours, training, behaviour) works the same.
- **Challenge status (M3-13, no free trial):** `payment_required` (unpaid — from creation on, also while unborn, so the parent can buy before the contract) → `paid`. `Pet::giveBirth` sets `trial_ends_at = born_at` (column kept, expand-only). `trial` remains only for (a) a pet born before M3-13 whose 7-day trial is still running (`now < trial_ends_at`, kept until its end — no retroactive lock), (b) any unpaid challenge while `payments.enforced` is false (kill switch: `trial` = "unpaid, playable"), (c) a born row without `trial_ends_at` written outside the model. An unborn pet is never payment-locked and its lock reason stays `contract_required` (`Pet::awaitsPayment` ignores unborn pets), so the child can always sign.
- **Lock at birth (M3-13):** `PetActivityService::signContract` first assigns a held credit (`ChallengeCreditService::assignAvailableBeforeBirth`: own transaction, family → pet → credit; only if the family has an available credit AND this unborn pet is its only active unpaid challenge pet — `assigned_via = birth`), then births the pet and calls `ChallengeService::lockAtBirth` under the same row lock: `payment_locked_at = born_at`, non-quiet save (freeze + `payment_lock` period from the birth), lock push (`metric no_trial`), no extra broadcast (the contract's `PetUpdated('signed_contract')` carries the locked plan). Payments not enforced → no lock at birth; if enforcement is switched on later the tick locks such a pet from that tick (`processTrials`: a pet without a trial is locked from now, never back to its birth — it was playing).
- **`payment_required` = lock** (new lock reason, like hard stop): decay / escalation / illness counters / training decay paused; child sees a kind locked screen ("Starš mora odkleniti nadaljevanje"); parent sees the paywall for that pet. On payment the pet resumes where it stopped (pause time does not count against needs).
- **Program clock (P9, M3-11b):** time inside `payment_lock` status periods is not program time. The 12-week clock (`virtual_age_months`, `hasReachedSimulationEnd`, certificate), the dog's age / life stage (`LifeStageService`) and the per-child 12-week progress all run from an effective birth = `born_at` + payment-lock seconds before the instant (capped at the lock start while locked). Every lock period counts (lock at birth, expired pre-M3-13 trial, refund re-lock); admin unlock / purchase closes it — **since M3-13 the 12 weeks effectively start at the purchase.** **Lock start** (`payment_locked_at` = period start): a lock at birth starts at the birth; an expired pre-M3-13 trial is locked from `trial_ends_at` even when the tick runs later (scheduler outage) — that gap is not program time; a pet without a trial that the tick locks (born while payments were not enforced, admin-created) is locked from the tick; a refund re-lock starts at the refund (the pet was paid and in play until then). Never before the end of the previous lock, never in the future. Hard stop, illness and inactive periods still count. `born_at` and `trial_ends_at` never change.
- **Credits:** each successful store purchase (RevenueCat NON_RENEWING_PURCHASE / INITIAL_PURCHASE of the consumable, idempotent by event id) creates one **challenge credit** for the buyer's family. A credit is assigned to exactly one pet. Assignment: the app calls `POST /api/parent/pets/{pet}/challenge/activate` after the purchase (idempotent; uses the oldest unassigned credit; 409 `no_credit` if none); the webhook auto-assigns when the family has exactly one unpaid challenge pet (unborn included — buying before the contract pays that pet). Unassigned credits stay for later pets; at a birth the same "exactly one unpaid" rule assigns a held credit (M3-13). **Purchase intent (M6-U01, David »da« 2026-11-10, FREE_PET_UPGRADE_SPEC §5.3):** a new app calls `POST /api/parent/pets/{pet}/challenge/intent` right before the store sheet (parent only — `PetPolicy@buyChallenge`; per parent = the RevenueCat app user; single use; 30 min; a new one supersedes the parent's older one; same eligibility as activation: an unpaid challenge pet or an upgradeable free pet) and opens no sheet when it fails. The webhook with an intent valid at the purchase time assigns the credit to that pet (`assigned_via = intent`; a free pet is upgraded on the activation path) and consumes it; an intent whose pet is no longer eligible counts as none; the intent current at the purchase wins even when a later intent of the same parent superseded it (QA #978 a); **an intent for a FREE pet never takes the purchase from the family's only `payment_required` pet** — that pet gets it by the old rule (the purchase may come from an older app on another phone) and admins get a Discord `intent_overridden` alert to sort out the upgrade by hand (QA #978 b, a paid-for pet never stays locked). **Without an intent the webhook works exactly as before** (every older app) — a free pet is never auto-assigned. The new app still calls activate after the purchase (idempotent) and, on launch, shows »Imate neporabljen nakup — izberite ljubljenčka« while `credits_available > 0` and a pet can take it. **Safety net:** a credit still unassigned 10 min after the webhook in a family with a `payment_required` pet or an intent → one Discord alert per credit (`billing:unassigned-credits-check`). `assignAvailableBeforeBirth` and restore are unchanged.
- **Refund** (CANCELLATION of the consumable / REFUND): the credit is revoked; an upgraded free pet (M6-U01) goes back to the free plan (`challenge_started_at` cleared; a new purchase = new 12 weeks, K7); otherwise if it was assigned and the challenge is not finished, the pet goes back to `payment_required` and — if born — is locked at once (an unborn pet is never locked: one `PetUpdated('challenge_refunded')`, the lock comes at birth; QA PR #83 M1) (only a pre-M3-13 pet still inside its old 7-day trial goes back to `trial`).
- **Existing pets** (created before this release, testers): `plan = challenge`, status `paid` with source `grandfathered` — nobody gets locked by the deploy.
- **Display (M5-F02, David 2026-10-07: a mutt is never "Paid"):** `plan.display_type` = `free` for a free pet and for a pet of a breed without premium (the mutt) whose challenge is paid but not by a purchase (`grandfathered` / `admin`); else = `type`. Display only for **paid** mutts (no data change for them) — the real plan, program clock, history, certificate and media tier stay unchanged (no data migration). A purchased challenge stays "Paid".
- **Unpaid mutt challenges → free (M5-F02 QA, migration `2026_10_21_120000`):** a mutt with `plan = challenge` and no payment (trial, payment_required, unborn) becomes `plan = free` via `ChallengeService::convertUnpaidMuttToFree` (row lock, non-quiet save): an open payment lock is lifted like a payment (period closed now, thaw, decay clock restart); `pets.converted_to_free_at` keeps its past `payment_lock` periods out of the program clock. No media change, no push; one `PetUpdated('plan_free')` per converted pet. Since then no path creates an unpaid mutt challenge: `Pet::creating` defaults the plan by breed (`PairingService::defaultPlanFor`) and turns challenge + breed without premium + unpaid into `free` (Filament, seeders, `/child/pair`, old PINs); **a refund of a mutt's challenge** (`ChallengeService::markRefunded`) makes it the free mutt (same bookkeeping, `converted_to_free_at`) instead of re-locking it. CHECK `pets_converted_free_check`: `converted_to_free_at` only on a free pet. *(The P7 "one trial per child" rule this sentence referred to was retired by M3-13.)*
- **Reminders (M3-13):** no "trial ends tomorrow" push any more (`trial_ending` stays in the enum / CHECK for stored rows, never sent). One push when the lock starts (in the device language, M1-18): parents "Kuža varno čaka, dokler v aplikaciji ne odklenete 12-tedenskega izziva" (metric `no_trial`; a pre-M3-13 trial that ends keeps "Brezplačni preizkus je končan …"), child "Igra počaka na starša".
- **»Želje« purchases (M6-W02, SHOP_SPEC, `docs/engineering/WISHES_API.md`):** separate consumables `petprep_wish_bed`, `petprep_wish_bowls`, `petprep_wish_toy_1`, `petprep_wish_toy_2` (5,99 €), `petprep_wish_treats_10` (2,99 €), `petprep_wish_bundle_welcome` (15,99 €) — config `services.revenuecat.wish_products` (env `REVENUECAT_WISH_PRODUCTS`, `product_id:item_key` pairs). The same webhook writes one **wish credit** (`wish_credits`) per purchase — never auto-assigned; the app calls `POST /api/parent/pets/{pet}/items/redeem` (`Idempotency-Key` = store transaction id) right after the purchase (409 `no_credit` → retry). Refund (CANCELLATION without expiration / REFUND) revokes the credit and removes the pet's items of that purchase (treats: the pack's unused treats); TRANSFER moves unassigned wish credits; SANDBOX follows `accept_sandbox`. No refund on game over / pet deletion (S11). Available for free and challenge pets, not for game over / `payment_required`.
- **Credit sources (M6-S01, website gift voucher, `WEBSITE_SALES_SPEC.md` §3, CONTRACT M6-S01):** `challenge_credits.source` = `store` (RevenueCat purchase, `purchase_event_id` set — every credit before M6-S01) or `web_gift` (a Lemon Squeezy gift voucher redeemed on petprep.si, `gift_voucher_id` set, `purchase_event_id` null, `store = LEMON_SQUEEZY`, `purchased_at` = the redemption moment). A gift credit is an ordinary held purchase: never auto-assigned at redemption (the parent chooses the pet with `…/challenge/activate`; oldest credit first across both sources), it pays the only unborn pet at birth like any held credit, `challenge_paid_source = purchase` (full media, deletion warning P5, refund rules as below), counted in `credits_available` (the existing »unused purchase« prompt — no new API field, the app is unchanged and never mentions vouchers). **RevenueCat never touches a gift credit:** refund matching (`revokeForRefund`), TRANSFER and the unassigned-credit alert only look at `source = store` (for store-only families byte-for-byte as before — regression tests R1–R9). A voucher is valid 12 months from purchase (server rule); a credit, once redeemed, never expires. **Gift refund:** Lemon Squeezy `order_refunded` (full) or a disabled license key → the voucher is `refunded` / `disabled`; a redeemed voucher's credit is revoked through the same `revokeCredit` → `ChallengeService::markRefunded` (lock, or back to the free plan; nothing after the 12 weeks); a partial refund only alerts an admin. Redemption is behind the admin switch »Gift vouchers« (default OFF); refunds are processed either way. **Who gets the credit (M6-S01b, David 2026-11-11):** the family of the parent who is SIGNED IN on the redeem page (Google / Apple / e-mail + password, the same account as in the app — `POST /api/web/parent-session` → a 15-minute `gift:redeem` token accepted only by `POST /api/gift/redeem`); no e-mail is typed for redemption (the M6-S01 e-mail lookup is gone). App tokens can never redeem (401) — the app still has no code field and never mentions vouchers.
- **Purchases only in the parent app** (password-protected = parental gate); never in a child session.
- **Deletion (P5):** a deleted pet's credit stays used (`challenge_credits.pet_id` → null, `assigned_at` kept). `DELETE /api/parent/children/{child}` and `POST /api/parent/account/delete` (last parent → family) answer 422 `paid_challenge_ack_required` + `pets: [{pet_id, breed_type}]` when a pet they would delete has a challenge paid by a purchase that is neither finished (12 weeks) nor game over, unless the body has `acknowledge_paid_challenge: true`. `GET /api/parent/billing` → `pets[].deletion_loses_purchase`. Admin (Filament) deletions are not gated.
- **AI media (P6):** `full` video set only when `challenge_paid_source = purchase`; unpaid (payment_required, a pre-M3-13 trial) / free / grandfathered → `basic`. Stored videos keep being served (a tier change never deletes or regenerates); a purchase queues the missing full-set videos; after a refund they stay (P10 — no 48 h delay). Stage transitions regenerate only the current tier's set. **Pool pets (M4-10):** the tier rule is the same, but a free pet's media come from its shared look — anything generated for it (basic set, a purchase's extra full-set videos, behaviour videos, stage images) is stored once on the look and reused by every later pet of that look for 0 $; a purchase keeps the look.
- **~~Trial per child (P7)~~ — retired by M3-13:** there is no trial to give. `trial_available` stays in the API for old builds (deprecated): `generate-pin` → always null; `GET /api/parent/billing` → `pets[].trial_available` true only for a born pet whose pre-M3-13 trial ran, else null — never `false`, which TestFlight 3.0.0 renders as "no free trial, the child already had one" (QA PR #83 m1). A game-over pet cannot be activated (422 `pet_not_active`).
